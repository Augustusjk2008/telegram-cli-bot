# Installation, Runtime and Release

## Installation and startup

- Windows installation: `install.bat`, `install.ps1`; startup: `start.bat`, `start.ps1`.
- Linux/macOS installation: `install.sh`; startup: `start.sh`.
- The installers check for Python 3.10+, Node.js 22.13+ and Git; the Node check and the download fallback must satisfy the frontend lockfile requirements. The Windows installer can optionally download the pinned Codex `0.121.0` and cloudflared `2026.3.0`; the Linux/macOS installer prompts the user to prepare Codex/Claude. Example plugins are skipped by default and can be enabled with the installer's `InstallExamplePlugins` / `--install-example-plugins` option.
- `install.ps1` installs dependencies with the detected Python; `install.sh` creates `.venv`. The source launch scripts prefer the project `.venv` and otherwise look for a system Python; when a startup step fails they install dependencies and retry at most once, `TCB_STARTUP_FORCE_DEP_INSTALL` forces a sync, and `TCB_STARTUP_USE_SYSTEM_PYTHON` is honored when creating the venv.
- `start.bat` puts the launch command and the exit handling after it in one pre-parsed code block: an update may replace the file while it is running, and cmd.exe would re-read it at the old offset. `start.ps1` and `scripts/service-status.ps1` read the JSON written by Python with `-Encoding UTF8` (Windows PowerShell 5.1 decodes with the ANSI code page by default).
- The source launcher first creates an executor snapshot outside the installation directory; an interrupted transaction is recovered first. A normal startup completes the `.env`, migration and import checks and then hands the host to an independent supervisor. Startup uses the existing `front/dist` directly and never rebuilds the frontend automatically; after frontend changes the user runs `npm run build` manually.
- `python -m bot` goes through `bot/__main__.py`, which first finishes storage migration finalization and runtime data migration and then calls `bot/main.py:main()`; the source launch scripts migrate beforehand and pass `--tcb-migrations-checked`. `main()` runs `asyncio.run(run_all_bots())` in a restart loop, starting the Web service and the Telegram gateway when it is enabled by configuration.
- An ordinary restart sets `RESTART_REQUESTED` / `RESTART_EVENT`, and the official supervisor handles exit code `75`; updates use a separate request and exit code `76`, and only consume a `waiting_restart` job. `CLI_BRIDGE_UPDATE_PROTOCOL=1` indicates the official launcher capability; a direct `python -m bot` only checks and prepares. Operations on the current host remain bound by the root `AGENTS.md`.

## Update transaction

- `bot/update_state.py` locates the installation-scoped state through the runtime paths and uses a normalized root-directory identity, revision numbers, atomic writes and OS file locks. `bot/update_service.py` unifies automatic/manual/offline/upload preparation; SSE only subscribes to the job, so a disconnect does not download again. The automatic check runs when the Web host starts and every 6 hours (`UPDATE_AUTO_CHECK_INTERVAL_SECONDS`); it only prepares and never applies, and it does not prepare again a version whose current job was cancelled or failed only after the download completed (only interrupted downloads are retried automatically); online preparation rejects a Release identical to the running version (`update_not_available`). Every state read recomputes `update_available` and reports the `preparation_log` / `runner_log` that already exist in the job directory. Uploads may carry `?size=`: an oversized upload is rejected early and a progress percentage is provided, and state writes during the upload are throttled and run in a thread. `state.json` is written as pure ASCII JSON. Legacy state only claims packages that can be proven to belong to the current installation and requires them to be prepared again.
- The installation locks of the host and the launcher live in a separate control directory, so migrating the data directory does not change the lock identity; a direct `python -m bot` also takes part in the mutual exclusion. The new host reports the current state path through a handoff file carrying the process identity, and the launcher re-reads it after an ordinary restart and after an update exit, so that pre-migration state is not consumed. After the official host starts, it moves the handoff path and token from `os.environ` into the in-process state of `bot/update_state.py`, so Agent, terminal and plugin child processes do not inherit them; `tests/conftest.py` also clears inherited update protocol variables to prevent tests run inside an Agent session from overwriting the live host's handoff file. New tasks are paused before health confirmation and opened after success or a safe recovery, and the accepted host then removes `TCB_UPDATE_JOB_ID` and `TCB_UPDATE_HEALTH_TOKEN`.
- The stages are `preparing → ready → waiting_restart → applying → awaiting_health → succeeded`; preparation can be cancelled/retried: cancellation only checks the job ID and stage (preparation progress advances the revision several times per second) and terminates the running pip/npm process tree; when a new job meets a failed, cancelled or not-yet-ready job for the same Release, it takes over that job's download checkpoint or its verified complete package. A failed application enters `rolling_back → rolled_back / recovery_required`. Application is bound to the job ID and revision and is blocked by running Agents, cluster tasks and storage migration; the Web host first verifies the hashes of all original and staged files in a thread, then closes admission and performs the idle check inside the event loop.
- `scripts/update_transaction.py` skips targets whose content and executable bit already match the staged file (no backup, no rewrite, logged as `unchanged_skipped`); for the remaining targets it copies and verifies all backups before replacing and records the operation intent on disk; replacements and deletions hit by transient Windows locks (winerror 5/32/33) are retried briefly; recovery copies the backups and is repeatable, the log records the target's original executable bit, and a target whose content is unchanged but whose executable bit differs is likewise restored from the backup (legacy logs without that field are judged by content only). On interruption the transaction directory is kept; when legacy `.update-apply-*` materials are incomplete, a manual recovery requirement is reported.
- `scripts/update_package.py` unifies verification of the manifest, version, archive paths, platform architecture, package type and file hashes. Configuration and the actual storage paths are protected; local source modifications and files of unknown ownership are kept as conflicts. An obsolete file must have its ownership proven by the old manifest.
- `bot/update_preparation.py` prepares the Python environment in a stable separate path and verifies the dependency fingerprint. The frontend package records the deployment parameters and asset hashes and is reused when they match; a rebuild uses a staging directory and `npm ci`. The skip-sync options do not authorize an update that fails the requirements.
- `scripts/update_runner.py` and its standard-library helper modules are copied to a fixed snapshot to run; the portable build's control Python lives outside the update target. The update is applied only after the old host exits and releases the installation lock. The health check of the new instance verifies the job, token, version, instance and actual listening address, waiting 180 seconds by default; `TCB_UPDATE_HEALTH_TIMEOUT_SECONDS` (30–1800) is written into the job when application is confirmed; before recovery, `host.lock` decides whether the host is still running, and the recorded PID is used only for legacy hosts that do not hold the lock; the instance is ready only when the frontend assets are complete and the necessary migrations have finished. External model, Telegram and tunnel status do not trigger recovery on their own.
- The old program and dependency environment are kept until health confirmation. After recovery the old version is verified again, and the result provides a retryable recovery command. Announcement sync is a separate follow-up action whose failure cannot change the successful state of the program update. Data migration compatibility is checked by `bot/update_migration_gate.py`, and a program rollback keeps user data.
- The first update from a legacy version uses `scripts/update_bootstrap.py` from the complete new package; for the parameters and order of operations see the two root READMEs; without Git or an old manifest, the complete package of the original version and its SHA-256 are needed to establish a baseline. The tool prepares first, the user applies explicitly after exiting the old service, and the bootstrap directory and recovery command are kept. When rolling back a legacy portable build, the executor only reuses the environment and PATH initialization of the restored `start.ps1` and then runs the old Python bootstrap; the elevation, migration and supervisor entry of the full launch script are not executed on this path.


## Release

```powershell
pwsh -ExecutionPolicy Bypass -File .release-local/publish-release.ps1 -Version <version> -RunChecks
pwsh -ExecutionPolicy Bypass -File .release-local/publish-release.ps1 -Version <version> -RunChecks -ReleaseNotesFile .\docs\release-notes\v<version>.md
```

- `APP_UPDATE_REPOSITORY` accepts a full HTTP(S) latest-release API URL returning GitHub Releases-compatible JSON (`tag_name`, `assets[].name`, `assets[].browser_download_url`); custom URLs are requested directly. Full GitHub repository URLs, including `.git`, `/releases` and `/releases/latest` suffixes, and legacy `owner/repo` values resolve to the GitHub latest-release API. The default is the full official repository URL; environment changes take effect after a backend restart.
- Online preparation is bound to a specific Release and asset; offline packages are provided by a host path or an administrator's streaming upload. The version, distribution marker and manifest must agree, and downgrades and incompatible platforms/package types are rejected by default.
- The Release body uses the Markdown specified by `-ReleaseNotesFile`; when it is omitted, `gh release create --generate-notes` is used.
- The default `-Mode BuildAndPublish` builds, commits the release changes, pushes the branch/tag and creates the GitHub Release; `BuildOnly` only builds, and `PublishOnly` reuses existing artifacts. `-RunChecks` is a build-stage option that runs `python -m pytest tests examples/plugins -q`, the frontend test gate and lint; the build flow additionally generates the frontend, the Windows portable package, the announcement snapshot, the legal files and the SHA-256 checksum files.
- The Windows portable build is produced by `.release-local/portable-win/build-portable.ps1`, pins Node `22.17.1`, and bundles Python, Git and the Python dependencies; the launcher inside the package uses its own bootstrap.
- `scripts/verify_release_legal_files.py` only checks that the required legal files and the portable runtime license files exist in the zip/tar. `scripts/update_package.py verify` independently checks the update protocol, the file manifest/hashes, the version and the commit identity. Both the PowerShell and Shell release entry points run both kinds of verification; `PublishOnly` must match the current commit and forbids dirty artifacts.
- `docs/` and the release notes stay outside Git; do not force-add them.
- The data directory as a whole is protected from updates; data files in an old manifest are never listed in the deletion plan either. The release manifest contains the actual source commit, the dirty flag, the dependency fingerprint, the frontend build parameters and the hashes of all program files.


## Runtime paths

- Fixed public forwarding pairs `frps` on the public server with the built-in `frpc` on the internal machine; configure `TCB_NODE_ID`, `WEB_BASE_PATH`, `WEB_FIXED_PUBLIC_FORWARD_*`, `TCB_HUB_FRPS_*`, `TCB_HUB_NODE_TOKEN` and `TCB_HUB_FRPC_*`, and the reverse proxy must retain the `/node/<node ID>/` prefix and support WebSocket. For the minimal configuration see the fixed public address and frp reverse proxy section of `README.md`.
- `bot/runtime_paths.py` distinguishes the storage root from the app data root. Before migration they are `~/.tcb` and `~/.tcb/orbit-safe-claw` respectively; `TCB_DATA_DIR` (environment variable or `.env`) only overrides the app data root.
- The committed `~/.tcb/storage.json` locator takes precedence in determining both roots; a missing target is an error, a conflicting `TCB_DATA_DIR` is rejected, and the current process freezes its paths until restart. For the migration flow see `bot/storage_migration.py` and `storage_runtime.py`; callers such as plugins, history and attachments should use the path functions.
- Storage migration moves `updates/<installation>/state.json`, but `updates/<installation>/jobs` (packages, staging, the frozen executor, transaction backups, the dependency environment) is installer material: it is not copied, its absolute paths are not rewritten, and cleanup leaves it in place, so that `python_executable` in the state and the recovery materials stay valid.
- `UpdateStore.prune_job_dirs()` only cleans valid job-ID subdirectories under `jobs/` of the current state root: it runs while holding `preparation.lock` (after `_reserve` creates a new job; the executor acquires it non-blockingly after `succeeded`/`rolled_back`). The current job, jobs referenced by any absolute path value in the state, by `sys.executable` (`abspath`, without resolving symlinks) or by the executor snapshot (`CLI_BRIDGE_UPDATE_RUNNER_PATH`), directories modified within 24 hours, directories whose transaction log does not end with `committed`/`rolled_back`, and links are always kept; nothing is cleaned when the current job is in the handoff, applying, recovery or an unknown stage, when the state is unreadable, or when a supervised host lacks the executor path. A failed deletion is only logged. When both the supervisor and host locks are free, `launcher-info` cleans `launcher-*` and control Python snapshots in the control directory that are older than 24 hours and not referenced by the state, the launcher pointer or the current process.
- Portable sets `TCB_PORTABLE_ROOT=<package>` and uses `<package>/.tcb` as an independent storage root, to avoid reading the host user's migration locator; the default app data is `<package>/data/orbit-safe-claw`. After a portable build is migrated, the locator inside the package decides the app data root and the default `TCB_DATA_DIR` override is cleared.
- Announcement content is obtained through `get_announcements_content_path()`; the repository root `.web_announcements.json` serves legacy data migration and the release package's announcement snapshot. User content should be written to the current runtime directory; existing repository-local runtime files (such as `.tcb/startup`, `.plugins` and `managed_bots.json`) are maintained by their own implementations and stay outside Git.

## Verification

- Launch scripts and executor: `tests/test_start_scripts.py`, `tests/test_update_runner.py`, `tests/test_update_preparation.py`. They use a simulated host and do not listen on a port.
- Runtime paths, migration and startup: `tests/test_runtime_paths.py`, `tests/test_storage_migration.py`, `tests/test_storage_runtime.py`, `tests/test_runtime_data_migrations.py`, `tests/test_main_migration_gate.py`, `tests/test_runtime_web_startup.py`; select by the change.
- Updater/release packaging: `tests/test_updater_release_packaging.py`; transaction checkpoints: `tests/test_update_transaction.py`; job isolation/API: `tests/test_update_service.py`. Real-platform update rehearsals are performed by the user on a separate test copy; the delivery distinguishes simulated results from real-platform verification.
- For behavior changes in Portable, archive legal files, announcement migration and safe extraction, prefer reusing `tests/test_updater_release_packaging.py`. Documentation checks do not run the release scripts; for an actual release, run the checks through the scripts and confirm the worktree and the release parameters.
